## 1. 安装与启动

### 1.1 最小安装 vs 全量安装

依赖分两层（D-5，2026-09-10 起）：

| 安装 | 命令 | 差异 |
|---|---|---|
| 最小（核心） | `pip install -r requirements.txt` | 15 个包。**Hub 可正常启动**；语义检索自动降级为 SQLite 关键词检索；Hub Agent 的 LLM 对话端点返回 `degraded` 提示而不是 500 |
| 全量（含向量栈） | `pip install -r requirements.txt -r requirements-vector.txt` | 再加 chromadb / sentence-transformers / langchain 等约 2GB，恢复语义检索与 LLM 对话链 |

其余功能（注册、心跳、任务、披露、通知、审计、团队联邦、Wiki、MCP）两种安装**完全一致**。

### 1.2 启动方式

| 方式 | 命令 | 说明 |
|---|---|---|
| 源码直跑 | `python main.py` | 日常开发/部署，端口读 `config.yaml` |
| 打包 exe | `python build_hub.py` | PyInstaller 打包（`sync_hub.spec` 已入库），产物无需 Python 环境 |
| Docker | `docker-compose up -d` | 多 Agent（20-50）场景 |

### 1.3 启动期的硬门（会直接拒绝启动，不是警告）

这些是**故意的**——静默跑起来比拒启危险：

| 现象 | 原因 | 修法 |
|---|---|---|
| `[FATAL] auth.registration=guarded 但 auth.hub_token 为空` | 受管注册必须有部署级凭据 | 填 `auth.hub_token`：`python -c "import secrets; print(secrets.token_urlsafe(32))"` |
| `[FATAL]` 证书相关 | `server.tls.enabled=true` 但证书/私钥不可用 | 修证书路径，或把 `server.tls.enabled` 置 false |
| `[FATAL] 检测到绑定 0.0.0.0:3060 但未找到对应防火墙规则`（仅打包版） | 对外暴露却没放行端口 | 按提示执行 `netsh advfirewall firewall add rule name='Sync Hub 3060' dir=in action=allow protocol=TCP localport=3060`，或改 `server.host: 127.0.0.1` |
| `[FATAL] NO_AUTH=1 在生产打包中不允许启动` | 测试后门不许进生产 | 去掉环境变量 `SYNC_HUB_NO_AUTH` |
| `[WARN] 监听 0.0.0.0 且未启用 TLS` | 只警告，不拦 | 对外必须解决，见 §8 |

### 1.5 客户端（接入方自建）

**本产品只交付 Hub 与通用 API，不自研客户端**（2026-09-21 方向裁决）。旧的 Electron 桌面端 （`E:\sync-hub-agent`）已冻结、退出交付面，不再维护。

接入方拿到凭据后（§2），用任意 HTTP / WS 客户端对接：

- REST：`/api/v1/*` —— 对外访问口径见 `docs/external-api-access.md`
- WS：`/ws/{agent_id}` —— envelope 分层协议（实现见 `envelope.py`）

> 协议层提醒：**平铺旧格式（`version<2`）自 2026-09-21 起不再接受**。原兼容分支只服务旧桌面端的 heartbeat 平铺帧，已随客户端一并下线（台账 CD-032）。新接入方一律用 envelope 格式。

## 2. 接第一个 Agent

### 2.1 认证模型

| 凭据 | 谁用 | 说明 |
|---|---|---|
| `hub_token` | 控制台 / 运维脚本 | 部署级单 token（`auth.hub_token`）。**等于全权，别发给外部方** |
| `api_key` | 每个 Agent | 注册时签发，绑定 role/department/capabilities |
| scoped key | 外部协作者 | 受限凭据，见 §8 |

`auth.registration` 两态：
- `open` —— 自注册（内网快，匿名可注册）
- `guarded` —— 受管注册：未预签发的 `agent_id` 一律 403，**角色由服务端决定**（推荐对外/生产）

### 2.2 open 模式（内网最快）

```bash
curl -s -X POST http://127.0.0.1:3060/api/v1/agents/register \
  -H "Content-Type: application/json" \
  -d '{"agent_id":"cs-wang","agent_name":"客服小王","department":"客服部",
       "role":"worker","capabilities":["客服对话"]}'
# 返回体里 api_key 明文只在注册/重注册回执里出现，自己存好
```

### 2.3 guarded 模式（推荐生产）

```bash
# ① 管理员预建身份（幂等；已存在返回 409，不覆盖）
python hub_cli.py agent create --id cs-wang --name "客服小王" \
    --role worker --department 客服部 --db ./sync_hub.db

# ② Agent 端用自己的凭据 bootstrap 换 api_key（带 hub_token 或预建记录）
```

### 2.4 角色与权限（三级）

| 角色 | 对应岗位 | 能做什么 |
|---|---|---|
| `worker` | 执行者 | 写自己的记忆；查自己的内容；**默认看不到别人的** |
| `manager` | 主管 | 看下属**摘要**（不是全文）；调度团队任务；过运维门 |
| `orchestrator` | 调度者 | 全局视角（仍受披露策略约束）；跨团队调度；过运维门 |

⚠️ 常见坑：Agent 端 `bootstrap` 的 payload 写死 `role: worker`，会**覆盖**之前 register 的 manager 角色。要提权得重新 register 带 `role`，直改数据库无效（内存 dict 与 DB 双写，直写 DB 不生效）。

## 4. 核心业务操作

### 4.1 记忆（写入隔离）

```bash
# 写（只有自己查得到；不广播）
curl -s -X POST "http://127.0.0.1:3060/api/v1/memory/store?agent_id=cs-wang" \
  -H "Authorization: Bearer <api_key>" -H "Content-Type: application/json" \
  -d '{"memory_key":"ticket-001","content":"客户反映浴室柜色差…","kind":"fact","tags":["售后"]}'
```

- 写入有**三段去重**：相似度 >0.90 合并、0.75~0.90 覆盖、<0.75 新增
- 版本历史：`GET /api/v1/memory/{key}/versions`（owner-only）；`POST …/rollback?version_id=N` 可回滚（回滚会重算向量，算不出就写 NULL ——「宁可暂时没向量，也不用错位向量」）

### 4.2 披露（这套系统的核心）

四级披露 + 8 条规则链：

| 级别 | 给什么 | 典型场景 |
|---|---|---|
| `NONE` | 什么都不给 | 默认隔离 |
| `METADATA` | 标签/时间/重要性 | 存在性查询、统计 |
| `SUMMARY` | 前 200 字 | 主管日常 |
| `FULL` | 全文 | 纠纷处理、需审批升级 |

走法（worker 想看别人的）：

```bash
# ① 发起披露请求 → 落 disclosure_requests（status=pending_approval）
# ② 审批人（manager/orchestrator）批准 → 级别提升
# ③ 24h 内没人处理 → 自动 rejected（惰性 TTL，不是永久 pending）
```

**口径（冻过）**：
- 权限不开第二套 —— manager 看下属内容**走披露审批流**，端点不设角色旁路
- 「资源存在但无权」与「不存在」**同响应**（防枚举）
- 无主体（匿名工具）一律 fail-closed 到摘要级
- 企业**已发布**内容（知识层命中）对全员可见到摘要级（`disclosure.published_public`，只提升不降级）

### 4.3 任务

状态机：`pending → assigned → in_progress → completed / failed / cancelled`。

```bash
# 创建（task_id + description 必填）
curl -s -X POST http://127.0.0.1:3060/api/v1/tasks/create \
  -H "Authorization: Bearer <api_key>" -H "Content-Type: application/json" \
  -d '{"task_id":"t-001","description":"处理客户投诉","required_capabilities":["售后"]}'

# 依赖 DAG：depends_on 建链，环检测 fail-closed；get /tasks 带 blocked_by 计算字段
# 状态迁移：POST /api/v1/tasks/{id}/start|complete|cancel|fail?agent_id=<自己>
# 描述更新：POST /api/v1/tasks/{id}/update?description=…（中文记得 URL 编码）
```

看板按状态分 4 列；被依赖阻塞的卡片带 ⛔ 徽标。

### 4.4 通知

站内（DB + WS + Agent stderr 推送）之外，可配**钉钉 webhook / SMTP 出站**（`notify_channels`），异步 fan-out 不阻塞主链路，结果落 `notifications.channel_status`。

```bash
curl -s -X POST "http://127.0.0.1:3060/api/v1/notifications/create?agent_id=cs-wang&title=…&body=…" \
  -H "Authorization: Bearer <api_key>"
```

### 4.5 知识库与 Wiki

- **知识条目**：写入需 manager/orchestrator 角色（`POST /api/v1/knowledge`）
- **Wiki**：知识/记忆会同步成 `wiki/` 下的页面；新条目先进**收件箱**（`wiki_inbox`，status=pending），审批人 approve 才发布 —— 这是刻意的「人工过一道」
- **审批人门**：approve/reject 需 manager/orchestrator（或 hub_token）；worker 403
- 同步是全量重建：页数多时耗时长（历史实测 6429 页 23-24s）→ 用 `background=1` + `/wiki/sync/status` 轮询
- 收件箱列表默认 100 条（`limit/offset/total/has_more`），积压可用 `POST /wiki/inbox/cleanup` 预演清理

> ⚠️ 知识库检索（Phase 1-6）目前是**待料**状态：链路可跑通（`corpus/` 26 篇样本 + `scripts/seed_kb.py`），但没有真实企业语料，所以**没有可对外报的质量数字**（recall@5 / p95 等）。别对客户承诺"语义检索准确率"，当前默认 provider 是 `hasher`（词面哈希），**不是语义模型**。

### 4.6 共享工作区（CRDT）

多 Agent 同时编辑同一文档，pycrdt CRDT 自动合并，WS 实时广播 + 协作者在线列表（awareness）。容量护栏见 `workspace` 段（房间空闲 30 分钟卸载、常驻房间水位告警）。

### 4.9 员工凭据账本（每人多把）

员工凭据是**账本**：一个员工可持多把，每把有自己的 `key_id`、标签、到期时间、状态和调用画像；
明文只在签发那一刻显示一次（库里只存 SHA256）。

```bash
# 列某员工的凭据（不含明文）
curl -s -H "Authorization: Bearer <hub_token>" \
  http://127.0.0.1:3060/api/v1/access/accounts/<emp_id>/keys

# 签发新的一把（不覆盖旧的；可带标签与到期）
curl -s -X POST -H "Authorization: Bearer <hub_token>" -H "Content-Type: application/json" \
  -d '{"label":"小王的备用钥匙","expires_at":"2026-12-31"}' \
  http://127.0.0.1:3060/api/v1/access/accounts/<emp_id>/key

# 只吊销一把（其余继续可用）
curl -s -X POST -H "Authorization: Bearer <hub_token>" \
  http://127.0.0.1:3060/api/v1/access/accounts/<emp_id>/keys/<key_id>/revoke

# 整人吊销（该员工全部凭据）
curl -s -X POST -H "Authorization: Bearer <hub_token>" \
  http://127.0.0.1:3060/api/v1/access/accounts/<emp_id>/revoke
```

- 控制台里在「身份供给」页点凭据列的**明细**看账本：状态、创建、到期、**最近使用**、**调用次数**
  （调用次数 = 真实请求数，一次请求 +1），并可逐把吊销
- 存量凭据（升级前签发的）在迁移时自动进账本，**老 key 原样继续可用**
- `employee_accounts.key_hash` 保留为「最近一把有效凭据」的镜像，仅供老代码/回滚路径读取

## 5. 审计

这套系统的卖点之一是「谁看了什么，全可追溯」。三条链 + 两种留痕：

| 链 / 记录 | 内容 | 位置 |
|---|---|---|
| 主链 `audit_log` | 业务事件哈希链 | SQLite |
| 披露链 `disclosure_log` | 每次披露判定 | SQLite |
| jsonl 滚动链 | `audit/memory_pool.jsonl`、`audit/transport.jsonl`，每 1000 行算窗口 hash 挂主链 | 文件 |
| 读审计 `gateway_read_log` | 谁读了哪个端点、命中几条、被剥离多少 | SQLite |
| 拒绝留痕 | 403/404 也落一行（`granted_level=denied`） | 同上 |

```bash
# 完整性校验（主链 + 披露链 + jsonl 窗口）
curl -s -X POST http://127.0.0.1:3060/api/v1/audit/verify \
  -H "Authorization: Bearer <hub_token>" -H "Content-Type: application/json" -d '{}'
```

```bash
# 校验可覆盖子区间：{"start_id": N, "end_id": M}
```

**读校验结果的正确姿势**（CD-073 起）：
- `valid=true` 的含义是「**没有未解释的断点**」，不等于"什么都没缺"→ 还要看 `declared_gaps`
- `declared_gaps` = 内容**确实丢了且不可恢复**、已用 `scripts/audit_declare_gap.py` 在主链上留痕的窗口
  （谁在何时登记、为什么丢，都查得到）。控制台审计页会把它们单独列出来，不会藏在绿灯里
- 发现窗口缺失时：**能用备份/归档恢复就先恢复**；确认不可恢复才声明——声明是最后的如实记账，不是消红工具

```bash
# 声明一段已丢失的窗口（幂等；会往主链追加 anchor_gap 事件）
python scripts/audit_declare_gap.py --file transport.jsonl --window w-5609-6608 \
    --reason "运行产物被 git checkout 回退，运行期增长段不可恢复" --declared-by "运维"
```

> ⚠️ **jsonl 是运行产物，不进版本库**（CD-073 起 `.gitignore` 忽略 `audit/*.jsonl`）。历史教训：它曾被 git 跟踪，
> 而项目习惯用 `git checkout -- audit` 还原测试产物 → 运行期增长段被回退、窗口锚指向不存在的内容（见 `known_limitations` L2-ANCHOR-002）。

**外部锚（可选，默认关）**：`audit.anchor_urls`（链头 hash POST 到域外接收方）与 `audit.tsa`（RFC3161 时间戳盖章）。

关键诚实点：**本地 `audit/anchor.txt` 与链同机同目录，只能防误删，不能作为「链没被整段重写」的证据**。要防篡改举证必须有域外锚（TSA / 另一台机器），见 §12。

## 8. 对外交付（把 API 给企业以外的人）

完整版见 `docs/external-api-access.md`，这里只放三步与边界。

```bash
# ① 预建身份（只是身份壳，不交付它的 api_key）
python hub_cli.py agent create --id ext-partner-a --name "外部集成方A" \
    --role worker --department proj-ext --db ./sync_hub.db

# ② 签发受限 key（明文只此一次可见）
python hub_cli.py key create --agent ext-partner-a \
    --endpoints "/memory/disclose,/memory/search,/tasks" \
    --methods "GET,HEAD" --data-domain proj-ext --level-cap summary \
    --expires 2026-12-31T00:00:00 --db ./sync_hub.db

# ③ 随时吊销
python hub_cli.py key revoke --key-id key-xxxxxxxxxxxx --db ./sync_hub.db
```

**前提：先开 TLS**（`server.tls`），否则 Bearer 是明文过网：

```yaml
server:
  host: 0.0.0.0
  tls: {enabled: true, certfile: ./config/server.crt, keyfile: ./config/server.key}
```
自签证书一条命令生成：`python scripts/gen_tls_cert.py --out ./config --hosts hub.corp.local,192.168.1.10`

**这把钥匙拿不到什么（fail-closed）**：

| 边界 | 语义 |
|---|---|
| 凭据/配置类端点一律拒绝 | `/keys`、`/access`、`/server`、`agents/quota|full-access|register|bootstrap` —— 不看白名单直接拒（否则"只读"钥匙能自我提权成全权） |
| 方法白名单 | 声明后精确匹配，不在名单 → 403 |
| 路径白名单 | 边界匹配（`/mem` **不会**放行 `/memory/*`） |
| WS 默认拒绝 | WS 全双工、绕过两层白名单，需 `scope.ws=true` 才放行 |
| 披露上限 | `level_cap` 与规则链结果取 `min`（叠加，不是旁路） |

**建议再收紧**：给对外身份设配额 `mode=reject`（默认 `alert_only` 只告警）；定期查 `key_created` / `key_revoked` / `read_deny` 审计；用 `--expires` 而非永久钥匙。

## 9. 团队联邦（多 Hub 互联）

两个 Hub 配对后，跨 Hub 查询走披露链，流量可选 AES-GCM 应用层加密。

1. A 侧 `pair/request` → 6 位配对码（5 分钟 TTL）
2. B 侧 `pair/accept`（配对码 + 对方局域网地址）
3. 配对后双方可用 `/team/disclose/remote` 跨 Hub 查

注意：URL 校验**拒 loopback**（防 SSRF，是正确设计）→ 同机双 Hub 必须用局域网 IP；跨 Hub 查询的机密内容看不到是**安全通过**（别当成 bug）。

## 10. 排障速查

| 症状 | 先查什么 | 常见原因 / 修法 |
|---|---|---|
| 起不来，无日志 | 看 stdout 的 `[FATAL]` 行 | §1.3 五种硬门（hub_token / 证书 / 防火墙 / NO_AUTH / 端口占用） |
| 所有请求 401 | `auth.enabled`、带上凭据了吗 | 忘带 `Authorization: Bearer`；或 token 与 Hub 配置不一致 |
| 页面能开但数据全 401 | localStorage 里的 token | 重新输入 `hub_token`（页面壳免认证，API 不免） |
| 健康检查 `status=degraded` | `warnings` 字段 | 多为 Agent 全离线；chroma 缺失也会降级（功能不受影响） |
| 语义检索结果像关键词 | `embedding.provider` | 默认 `hasher`（词面哈希）——不是语义模型，别称"语义检索" |
| `/health` 里 chromadb 不是 ok | 向量栈装了吗 | 最小安装就是 `disabled`，检索自动走关键词降级（响应带 `degraded=true`） |
| 知识/wiki 同步很慢 | 页数 | 全量重建：页多则慢，用 `background=1`；压测产物记得清 |
| 高并发下峰值入队延迟高于 3.59s 口径 | 认证行缓存开了吗 | 默认档最严（凭据变更**立即**生效）；要达峰值口径开 `SYNC_HUB_AUTH_ROW_CACHE=1`（TTL 8s，代价=凭据变更最迟 8s 生效）。口径与选项对照：`docs/d10-d11-perf-recheck-2026-09-14.md` §八 |
| Agent 连不上 | 端口/防火墙/hub_url | 局域网要用 `0.0.0.0` 监听 + 防火墙放行；Agent 端 `hub_url` 写对 scheme |
| Agent 频繁掉线 | WS 超时配置 | 客户端 socket 超时必须大于服务端 ping 间隔（既有实现已 35s > 20s） |
| 通知不出去 | `notify_channels` + `channel_status` | 凭据未配 / 渠道禁用；看 `notifications.channel_status` 里的错误 |
| 任务卡 pending | 状态机 | `pending` **不能直接 start**（要先去 assigned）；`blocked_by` 非空说明依赖没过 |
| 跑测试后生产数据变了 | —— | 不该发生（CD-070/070b 已堵）；若出现请立刻停下查 `_sync/` 里的排查脚本 |
| 端口被占 | `netstat -ano \| grep 3060` | 常见是上次测试的残留 Hub（3062-3074 段），按 PID 杀 |

排障纪律：**别用 `taskkill /f /im python.exe`** —— 会把 Hermes 主进程一起杀掉。按 PID 杀，或 `taskkill /F /T /PID <pid>`。

## 12. 已知限制（对客户承诺前必读）

| 编号 | 限制 | 影响 |
|---|---|---|
| — | 派单重放**不去重**：Hub 在 `hello` 时按 checkpoint 重放未确认派单，**幂等由接入方自行保证**（原 L1-EVICT-001/002 是旧桌面端实现的边界，该实现已不再交付） | 接入方需自行按 `dispatch_id` 去重 |
| L5-TIMEOUT-001 | 半开判定 = 30s 心跳 × 3 周期（90s），故意不用 1× 以容忍丢包/GC | 断连判定有最长 90s 延迟 |
| L2-ANCHOR-001 | 外部锚**默认未配**；本地 `audit/anchor.txt` 与链同机同目录 | **本地审计不构成防篡改举证**；要举证必须配域外锚（TSA 或另一台机器） |

其他如实说明：

- **审计链的 TSA 盖章默认关**（不联网）。开了之后判据是「被盖章的链头节点仍在链中」，链正常增长不会误报
- **限流是进程内计数**（每 IP 1000/s 默认），多进程/多机部署时不是全局配额
- **知识库检索没有质量数字**（待真实语料，见 §4.5）
- **不自研客户端**：Hub + 通用 API 是全部交付物；原 Electron 桌面端已冻结退出（2026-09-21 裁决），接入方自建客户端（§1.5）
- **PG 迁移未做**：当前是 SQLite 单机；约 76 个 async 函数仍在事件循环里直连 SQLite（已登记，随 PG 迁移一起换），高并发极端场景有延迟风险
