# 架构决策：数据底座主线（SQLite → PostgreSQL → 多 Hub 分片）

日期：2026-09-10 · 决策者：用户 · 起草：Hermes · 状态：**已定 —— 2026-09-14 入库（批 D 3-9 落档）**；文字表述如需修订请直接批注本文件

---

## 一、要决策的问题

仓库里同时存在两条数据底座演进路线，且已双向投入：

- **路线甲（FAQ 承诺）**：SQLite → PostgreSQL → 多 Hub 分片 —— 数据库横向扩展路线
- **路线乙（目标架构）**：主干-分干 git 联邦 —— 数据真相源为 git 仓库群，Hub 之间联邦同步（`data-trunk/` 影子双写已在 P0 落地）

两条并用意味着：数据访问层、审计链、迁移通道、容错语义都要同时满足两套假设，后续每个模块都要"双份兼容"。必须择一为主线。

---

## 二、决策

**主线 = 路线甲：SQLite → PostgreSQL → 多 Hub 分片。**

- **路线乙降级**为过渡 / 可选能力，定位改为「**审计与备份镜像**」——不再是主线数据通道。
- **现有 `data-trunk/` 影子双写与网关层保留不拆**（已落地的工，拆掉既白费成本又丢审计底座），仅在文档与台账中标注定位降级。
- FAQ / 架构文档中 PG 与分片的表述保留为**主线方向**（不再是"未来候选"）。

---

## 三、理由

1. **产品形态**：主线 = 企业本地部署 / 中心化多租户。Hub 面对的是"一个企业内部多 Agent 协同"，而不是"多个平等 Hub 之间的联邦协同"。甲匹配这个形态，乙假设的是另一种产品。
2. **交付成本**：甲只需替换存储引擎（迁移路径清晰：SQLite → PG → 分片）；乙要求"git 仓库群同时是运行时数据源"，等于把数据一致性问题交给 git 语义，长期维护成本高于换库。
3. **已有投资的处置**：乙的已落地部分（影子双写、网关读日志、审计镜像）在甲主线下不失效，降级为审计/备份用途即可，无需返工。

## 四、影响面（已并入批 D 计划）

| 对象 | 影响 |
|---|---|
| **3-1 db 异步化收口** | **改写**为「db 门面 + 慢查询护栏」：查库统一走一层门面（唯一入口），门面内部先用 `asyncio.to_thread` 跑 SQLite，**不换驱动、不深改**；存量 759 处调用点只迁热点路径。门面 = 将来替换为 `asyncpg` 的接缝。验收口径改为「慢查询可观测 + 门面为唯一入口 + 200 并发不劣于 3.59s 基线」 |
| **3-9 本项** | 本文件即 ADR，落 `docs/architecture-decision-data-backbone.md` |
| `data-trunk/` 影子双写、`routes_gateway.py`、`gateway_read_log` | 代码不变，文档/台账标注「非主线数据通道，备用审计镜像」 |
| **PG 迁移时点** | 待两件事就绪：① 3-1 门面底座落地（迁移时只换门面内部）；② 新 Agent 端 harness 就绪（与 alembic 0003 的迁移时机同一条依赖链） |
